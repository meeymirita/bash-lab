## 6.1 Три потока и перенаправление | short: Потоки и перенаправление | est: ~30 мин
### intro
**Слова шага:** *стандартные потоки*, *stdin*, *stdout*, *stderr*, *дескриптор*, *перенаправление* `>` `>>` `<` `2>` `2>&1`.

У любой программы есть три «трубы», через которые она общается с миром:

| Поток | Номер (дескриптор) | Куда идёт по умолчанию | Назначение |
|---|---|---|---|
| `stdin` | `0` | клавиатура | ввод |
| `stdout` | `1` | экран | результат работы |
| `stderr` | `2` | экран | сообщения об ошибках |

Оба вывода выглядят одинаково (оба на экране), но это **разные потоки**, и их можно направлять в разные места. Перенаправления:

| Запись | Что делает |
|---|---|
| `> файл` | `stdout` в файл (файл создаётся заново) |
| `>> файл` | `stdout` в конец файла |
| `< файл` | `stdin` из файла |
| `2> файл` | `stderr` в файл |
| `2>&1` | `stderr` туда же, куда сейчас `stdout` |
| `&> файл` | и `stdout`, и `stderr` в файл (короткая запись) |

Попробуем. `ls orders /нет-такой-папки` печатает и результат (список), и ошибку:

```bash run
cd /work/coffeeops
mkdir -p tmp
ls orders /нет-такой-папки
echo "--- ошибки убраны:"
ls orders /нет-такой-папки 2> /dev/null
echo "--- раздельно в файлы:"
ls orders /нет-такой-папки > tmp/out.txt 2> tmp/err.txt
echo "out.txt:"; cat tmp/out.txt
echo "err.txt:"; cat tmp/err.txt
echo "--- всё в один файл:"
ls orders /нет-такой-папки &> tmp/all.txt
cat tmp/all.txt
```

**Дописать, а не затереть:**

```bash run
echo "первая" > tmp/log.txt
echo "вторая" >> tmp/log.txt
echo "третья" >> tmp/log.txt
cat tmp/log.txt
wc -l < tmp/log.txt
```

**Порядок записи важен.** Оболочка читает перенаправления **слева направо**:

```bash run
ls /нет-такой > tmp/a.txt 2>&1
echo "a.txt:"; cat tmp/a.txt
ls /нет-такой 2>&1 > tmp/b.txt
echo "b.txt (пусто):"; cat tmp/b.txt
```

`> файл 2>&1` значит «сначала `stdout` в файл, потом `stderr` туда же, куда `stdout`» — всё в файл. А `2>&1 > файл` — «сначала `stderr` туда, куда сейчас `stdout` (экран), потом `stdout` в файл» — ошибка осталась на экране.

**Отправить своё сообщение в `stderr`:** `echo "ошибка" >&2` — «`stdout` этой команды в `stderr`». Так мы писали в `die` и `log` (шаг 5.2).

```bash run
bash -c 'echo "результат"; echo "сообщение об ошибке" >&2' 2> /dev/null
```

### result
```out auto
```

В последней команде мы убрали `stderr`, и осталась только строка «результат».

### why
Разделение потоков — основа того, как скрипты «разговаривают»: данные уходят по конвейеру дальше, а сообщения для человека не портят эти данные. Без понимания `2>&1` нельзя ни собрать журнал, ни разобраться, почему «ошибка не попала в файл».

### deep Как это выглядит внутри
Дескрипторы — это номера открытых «каналов» процесса. `>` у оболочки означает «перед запуском команды подключи дескриптор 1 к файлу»; `2>&1` — «сделай дескриптор 2 копией дескриптора 1». Программа этого не замечает: она просто пишет в «поток 1» и «поток 2». Поэтому порядок перенаправлений меняет результат: копируется то, куда указывает дескриптор **в этот момент**.

### deep Как ещё можно
- `> /dev/null 2>&1` (или `&> /dev/null`) — отбросить весь вывод. Мы разберём `/dev/null` в следующем шаге.
- `exec > файл` внутри скрипта направляет весь дальнейший вывод в файл.
- `set -o noclobber` запрещает `>` затирать существующий файл (обойти: `>|`).

### deep Если не получилось
- **Файл пустой** — перенаправлена не та часть (`>` — только `stdout`; ошибки нужны через `2>`).
- **`cannot create … Is a directory`** — вместо файла указана папка.

## 6.2 /dev/null, tee, here-doc и here-string | short: /dev/null, tee, here-doc | est: ~30 мин
### intro
**Слова шага:** `/dev/null`, `tee`, *here-doc* `<<`, *here-string* `<<<`.

**`/dev/null`** — «чёрная дыра»: всё, что в неё записано, исчезает; чтение даёт пустоту. Нужна, чтобы «отбросить» вывод или проверить успех без шума:

```bash run
cd /work/coffeeops
ls /нет-такой 2> /dev/null
echo "код: $?"
if grep -q "latte" orders/2026-10-01.csv 2> /dev/null; then echo "найдено"; fi
command -v shellcheck > /dev/null && echo "shellcheck установлен"
```

**`tee`** — «тройник» (как в водопроводе): копирует то, что читает со `stdin`, и на экран, и в файл. Полезно, когда вывод нужен и тебе, и в журнал:

```bash run
echo "заказ принят" | tee tmp/tee.txt
echo "заказ выдан" | tee -a tmp/tee.txt
cat tmp/tee.txt
```

(`-a` — дописать, а не затереть.)

**Here-doc** (*«документ здесь»*) — многострочный текст прямо в скрипте, который подаётся команде на `stdin`:

```bash run
name="Анна"
cat <<EOF
Здравствуйте, $name!
Ваш заказ готов.
Сегодня: $(echo "понедельник")
EOF
cat <<'EOF'
Здесь ничего не раскрывается: $name и $(date)
EOF
```

Слово после `<<` (здесь `EOF`, можно любое) — метка конца: текст читается до строки, где написана **только** метка. Без кавычек вокруг метки переменные и `$(…)` **раскрываются**; с кавычками (`<<'EOF'`) — нет, текст буквальный. Так мы записывали файлы командой `cat > файл <<'EOF'` — теперь ты понимаешь, как она работает.

**Here-string** `<<<` — одна строка на `stdin` (мы уже использовали её с `read`):

```bash run
wc -w <<< "один два три четыре"
tr 'a-z' 'A-Z' <<< "latte"
```

### result
```out auto
```

### why
`/dev/null` и `tee` — два инструмента, которые делают скрипты тихими или, наоборот, «записывающими». А here-doc — самый удобный способ положить в скрипт конфиг, письмо, SQL или справку, не заводя отдельных файлов.

### deep Как ещё можно
- `<<-EOF` — вариант, в котором начальные **табуляции** (не пробелы) в строках отбрасываются: удобно, когда here-doc внутри отступов.
- `/dev/null` не только «выбрасывает»: чтение из неё сразу даёт конец файла (мы использовали это в `read < /dev/null`).
- Для вывода сразу в два места и без экрана: `команда | tee файл > /dev/null`.

### deep Если не получилось
- **Скрипт «ждёт» бесконечно** — не найдена метка конца here-doc: она должна быть на отдельной строке, без пробелов в начале и в конце.
- **Переменные не раскрылись** — метка написана в кавычках (`<<'EOF'`).

## 6.3 Конвейеры | short: Конвейеры | est: ~30 мин
### intro
**Слова шага:** *конвейер (pipe)* `|`, *параллельные процессы*, `sort`, `uniq -c`, `cut`, `tr`, `PIPESTATUS`.

**Конвейер** `a | b | c` соединяет `stdout` одной команды со `stdin` следующей. Это главный приём Unix: маленькие программы делают одно дело и собираются в цепочку.

Все команды конвейера запускаются **одновременно** и работают, как рабочие на конвейере: пока вторая обрабатывает первую порцию, первая уже готовит следующую.

```bash run
cd /work/coffeeops
start=$(date +%s)
sleep 1 | sleep 1 | sleep 1
echo "прошло секунд: $(( $(date +%s) - start ))"
```

Три `sleep 1` подряд заняли бы 3 секунды, а в конвейере они идут одновременно — около одной.

Соберём «топ товаров» по шагам. Берём второй столбец (название товара) всех файлов заказов:

```bash run
cut -d, -f2 orders/*.csv | head -n 5
```

`cut -d, -f2` — «разделитель запятая, поле 2». В выводе есть и слово `item` из заголовков, убираем его:

```bash run
cut -d, -f2 orders/*.csv | grep -v '^item$' | sort | uniq -c
```

`grep -v` — «все строки, кроме подходящих»; `sort` — сортировать (нужно, чтобы одинаковые строки встали рядом); `uniq -c` — схлопнуть подряд идущие одинаковые и посчитать (`-c` — *count*). Теперь по убыванию и первые три:

```bash run
cut -d, -f2 orders/*.csv | grep -v '^item$' | sort | uniq -c | sort -rn | head -n 3
```

`sort -rn` — численная сортировка (`-n`) в обратном порядке (`-r`); `head -n 3` — три первые. Ещё пара полезных помощников:

```bash run
echo "latte espresso" | tr 'a-z' 'A-Z'
echo "a:b:c" | tr ':' '\n'
printf 'b\na\nb\n' | sort -u
printf 'x\n' | wc -l
```

`tr` — заменить символы одни на другие; `sort -u` — сортировать и убрать дубли.

**Код завершения конвейера.** Без `pipefail` код конвейера — код **последней** команды (мы видели в шаге 4.3). Посмотреть код каждой команды по отдельности можно через `PIPESTATUS`:

```bash run
false | true; echo "статусы: ${PIPESTATUS[@]}"
```

(Квадратные скобки — это массив, их разберём в сессии 7: пока читай «список кодов всех команд последнего конвейера».)

### result
```out auto
```

### why
Конвейер — это «слова» языка Unix. Умея соединять `cut`, `sort`, `uniq`, `grep`, `head`, ты за минуту строишь отчёт, который иначе пришлось бы программировать. `pipefail` и `PIPESTATUS` нужны, чтобы не пропустить ошибку в середине цепочки.

### deep Как ещё можно
- `sort -t, -k3 -n` — сортировка по третьему полю с разделителем `,`.
- `uniq -c` считает **только соседние** строки — потому перед ним всегда нужен `sort`.
- Если нужно разбить вывод по «слова на строки»: `tr ' ' '\n'`.
- Для сложных отчётов вместо цепочки команд берут `awk` (сессия 8).

### deep Если не получилось
- **Счётчики «не те»** — забыт `sort` перед `uniq -c`.
- **`broken pipe`** — потребитель (например, `head`) закончил раньше, чем производитель: это нормально и обычно скрыто.

## 6.4 xargs, find -print0 и подстановка процессов | short: xargs и find | est: ~30 мин
### intro
**Слова шага:** `xargs`, `find`, `-print0`, *подстановка процесса* `<( )`.

Не все команды читают список со `stdin`: `rm`, `cp`, `wc` хотят имена **аргументами**. **`xargs`** превращает вход в аргументы: читает строки со `stdin` и вызывает команду, подставляя их.

```bash run
cd /work/coffeeops
printf '%s\n' a b c | xargs echo "список:"
printf '%s\n' a b c | xargs -n 1 echo "по одному:"
printf '%s\n' a b c | xargs -I{} echo "файл {}.txt"
```

**Ключи:** `-n 1` — по одному элементу за вызов; `-I{}` — подставить элемент вместо `{}` (в любом месте команды); `-P 4` — запускать до 4 вызовов параллельно.

**`find`** ищет файлы по условиям. В паре с `xargs` — основа массовых операций:

```bash run
find orders -name '*.csv' | sort
find . -type f -name '*.sh' -newer seed.sh | sort | head -n 3
find orders -name '*.csv' -print0 | xargs -0 wc -l
```

`-name` — по шаблону имени; `-type f` — только файлы (`d` — папки); `-newer файл` — новее файла. **`-print0` и `xargs -0`** — особая пара: имена разделяются не переводом строки, а нулевым символом. Так не ломаются имена с пробелами:

```bash run
touch "tmp/iced latte.csv" tmp/tea.csv
echo "--- без -print0 (ломается на пробеле):"
find tmp -name '*.csv' | sort | xargs ls 2>&1
echo "--- с -print0 / -0:"
find tmp -name '*.csv' -print0 | xargs -0 ls
```

**Подстановка процесса `<( команда )`** подставляет вывод команды как *имя файла* — для команд, которые принимают только файлы:

```bash run
diff <(sort orders/2026-10-01.csv) <(sort orders/2026-10-02.csv) | head -n 5
echo "строк в трёх файлах:" $(wc -l < <(cat orders/*.csv))
```

### result
```out auto
```

### why
`xargs` и `find` — это «массовые операции»: удалить старые логи, пожать все файлы, прогнать проверку по каждому. `-print0`/`-0` защищает от имён с пробелами, а `<( )` избавляет от временных файлов.

### deep Как ещё можно
- `find … -exec команда {} \;` — то же без `xargs` (одна команда на файл), а `-exec … {} +` собирает много файлов в один вызов.
- `xargs -P 4 -n 1` — параллельная обработка: удобно для «сжать 100 файлов».
- `find -mtime +7` — файлы старше 7 дней; `-size +1M` — крупнее мегабайта; `-delete` — удалить найденное (**сначала запусти без него**).

### deep Если не получилось
- **`xargs: unmatched double quote`** — в именах есть кавычки: используй `-print0` / `-0`.
- **`find: paths must precede expression`** — шаблон `*.csv` оболочка раскрыла сама; ставь его в кавычки: `-name '*.csv'`.

## 6.5 🔨 Сломать → починить: тихие ошибки конвейеров | short: Сломать → починить | est: ~25 мин
### intro
:::trap Сломать → починить
Три ошибки, которые не шумят. Воспроизведи и почини.
:::

**Ошибка 1 — конвейер молчит об ошибке:**

```bash run
cd /work/coffeeops
cat orders/нет.csv | wc -l
echo "код: $?"
```

`cat` не нашёл файл (ошибка), но `wc` отработал, и код конвейера — `0`. **Почини:** `set -o pipefail`:

```bash run
bash -c 'set -o pipefail; cat orders/нет.csv | wc -l; echo "код: $?"'
```

**Ошибка 2 — файл затирается раньше, чем прочитан:**

```bash run
printf 'b\na\nc\n' > tmp/list.txt
sort tmp/list.txt > tmp/list.txt
echo "после sort > тот же файл:"
cat tmp/list.txt
echo "(пусто!)"
```

Оболочка открывает `> файл` для записи (и обнуляет его) **до** запуска `sort`, а тот читает уже пустой файл. **Почини:** писать во временный файл и переименовывать, или `sort -o` (у `sort` есть ключ для записи в тот же файл):

```bash run
printf 'b\na\nc\n' > tmp/list.txt
sort tmp/list.txt > tmp/list.sorted && mv tmp/list.sorted tmp/list.txt
cat tmp/list.txt
```

**Ошибка 3 — переменная теряется после `| while`:**

```bash run
count=0
printf 'a\nb\nc\n' | while read -r line; do
  count=$((count + 1))
done
echo "после конвейера: count=$count"
count=0
while read -r line; do
  count=$((count + 1))
done < <(printf 'a\nb\nc\n')
echo "с подстановкой процесса: count=$count"
```

Часть конвейера после `|` выполняется в **подпроцессе**, и изменения переменных не возвращаются в основную оболочку (как в шаге 4.2). **Почини:** `< <(команда)` или `< файл`.

### result
```out auto
```

### why
Все три ошибки молчаливы: ни сообщения, ни остановки — просто неверный результат. Теперь ты знаешь, где искать: `pipefail`, порядок чтения/записи файла и подпроцессы в конвейерах.

### deep Как ещё можно
- `sort -o файл файл` и `sed -i` (сессия 8) умеют менять файл «на месте» безопасно.
- Для подсчёта внутри цикла без подпроцесса: `shopt -s lastpipe` (в скриптах) — последняя команда конвейера выполняется в основной оболочке.

### deep Если не получилось
- **Результат отличается** — запускай блоки в том же порядке; перед блоком 2 очищается `tmp/list.txt`.

## 6.6 Проект: отчёт «топ товаров» | short: Проект: топ товаров | est: ~30 мин
### intro
**Слова шага:** *отчёт*, *конвейер из команд*, *функции*, *опции*.

Сначала — одна строка. «Топ-3 товара по числу заказов»:

```bash run
cd /work/coffeeops
cut -d, -f2 orders/*.csv | grep -v '^item$' | sort | uniq -c | sort -rn | head -n 3
```

Теперь тот же отчёт понятным скриптом с опциями (`-n` — сколько позиций, `-d` — папка с заказами), на нашей библиотеке:

```bash run
cat > bin/top.sh <<'EOF'
#!/usr/bin/env bash
# Топ товаров по числу заказов. Использование: top.sh [-n ЧИСЛО] [-d ПАПКА]
set -euo pipefail
ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
# shellcheck source=../lib/common.sh
source "$ROOT/lib/common.sh"

usage() { echo "Использование: top.sh [-n ЧИСЛО] [-d ПАПКА]"; }

n=5
dir="$ROOT/orders"
while getopts ":n:d:h" opt; do
  case "$opt" in
    n) n="$OPTARG" ;;
    d) dir="$OPTARG" ;;
    h) usage; exit 0 ;;
    *) usage >&2; exit 2 ;;
  esac
done

[[ "$n" =~ ^[0-9]+$ ]] || die "-n должно быть числом, а не '$n'" 2
[[ -d "$dir" ]] || die "нет папки '$dir'" 2

items_of() {
```

**По частям.** Функция `items_of` скрывает «трудную» часть конвейера под понятным именем; сам отчёт читается слева направо: «товары → отсортировать → посчитать → по убыванию → первые N».

### why
Одна строка пригодна для разовой задачи, а скрипт с опциями и проверкой входа — для повторного использования. Хороший приём: сначала собрать конвейер в терминале по шагам, потом оформить в скрипт.

### deep Как ещё можно
- Подсчёт по количеству штук, а не по числу заказов (с учётом `qty`) делает `awk` — в сессии 8.
- Вывод в файл с журналом: `./bin/top.sh | tee tmp/top.txt`.

### deep Если не получилось
- **`cut: … No such file`** — в папке нет `*.csv`; запусти `bash seed.sh`.
- **Пустой отчёт** — в файлах только заголовки.
