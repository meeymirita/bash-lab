## 2.1 Файл-скрипт, shebang и три способа запуска | short: Скрипт и запуск | est: ~25 мин
### intro
**Слова шага:** *скрипт*, *shebang*, *интерпретатор*, `chmod +x`, `source`, *дочерний процесс*.

**Скрипт** — обычный текстовый файл с командами. Вместо того чтобы набирать их по одной, ты записываешь их в файл, и оболочка выполняет сверху вниз. Начнём. Войди в контейнер (шаг 1.2), перейди в проект и создай первый скрипт:

```bash run
cd /work/coffeeops
cat > bin/hello.sh <<'EOF'
#!/usr/bin/env bash
echo "Добро пожаловать в CoffeeOps"
EOF
chmod +x bin/hello.sh
./bin/hello.sh
```

**Первая строка `#!/usr/bin/env bash`** называется *shebang* (читается «шебанг»; `#!` — «решётка-восклицание»). Она говорит системе: «этот файл надо запускать программой `bash`». Часть `env bash` значит «найди `bash` в `PATH`» — это надёжнее, чем жёсткий путь `/bin/bash`, потому что на разных системах bash лежит в разных местах (в нашем контейнере — в `/usr/local/bin`). Для оболочки это строка-комментарий (всё после `#` игнорируется), а для системы — инструкция.

Запустить скрипт можно тремя способами, и они **не равны**:

```bash run
./bin/hello.sh
bash bin/hello.sh
source bin/hello.sh
```

- `./bin/hello.sh` — запуск как программы: нужен `chmod +x` и shebang; создаётся **новый процесс** bash.
- `bash bin/hello.sh` — ты сама говоришь, чем запускать: права `x` не нужны, shebang игнорируется; тоже новый процесс.
- `source bin/hello.sh` (короче: `. bin/hello.sh`) — команды выполняет **твоя текущая оболочка**, нового процесса нет.

В чём разница на практике? Создадим скрипт, который задаёт переменную:

```bash run
cat > bin/setvar.sh <<'EOF'
GREETING="привет"
EOF
chmod +x bin/setvar.sh
./bin/setvar.sh
echo "после запуска: [$GREETING]"
source bin/setvar.sh
echo "после source: [$GREETING]"
```

### result
```out auto
```

После `./bin/setvar.sh` переменная пуста, а после `source` — на месте: дочерний процесс не может изменить переменные родителя (как человек в соседней комнате не может переставить мебель у тебя), а `source` выполняет команды прямо у тебя.

### why
Эта разница объясняет, когда нужен `source`: для подключения настроек и библиотек (сессия 5), — и почему скрипт «запускается, но переменные потом не видны». Shebang и `chmod +x` превращают файл в настоящую команду — основа всего, что мы напишем дальше.

### deep Как это выглядит внутри
Запуская `./bin/hello.sh`, оболочка просит систему выполнить файл; система читает первую строку, видит `#!/usr/bin/env bash` и сама запускает `bash bin/hello.sh`. Если shebang нет, оболочка пробует выполнить файл как скрипт своим интерпретатором — но на это нельзя полагаться (в другой оболочке будет иначе), поэтому shebang пишут всегда.

### deep Если не получилось
- **`Permission denied`** — нет права `x`: `chmod +x bin/hello.sh`.
- **`No such file or directory`** — ты не в папке `/work/coffeeops` (`pwd`), либо опечатка в пути.
- **Текст не на русском/кракозябры** — терминал не в UTF-8; в нашем контейнере кириллица работает, проверь, что ты именно в нём.

## 2.2 Переменные: объявление, окружение | short: Переменные | est: ~30 мин
### intro
**Слова шага:** *переменная*, *присваивание*, `${имя}`, `readonly`, `export`, *переменная окружения*.

**Переменная** — именованная ячейка с текстом. Положить значение: `имя=значение` (**без пробелов вокруг `=`** — это главная ошибка новичка, ниже сломаем её нарочно). Прочитать: `$имя`.

```bash run
name="latte"
price=180
echo "$name стоит $price"
echo "${name}s"
echo "$names"
```

**Команда по частям.** `name="latte"` — присваивание; `price=180` — число тоже хранится как текст; `$name` — подставить значение; `${name}s` — фигурные скобки отделяют имя от букв, которые идут следом (иначе bash искал бы переменную `names`, которой нет, — и подставил бы пустоту без ошибки).

Имена переменных — латиница, цифры и `_`, не с цифры; по соглашению свои переменные пишут `строчными`, а переменные окружения и константы — `ЗАГЛАВНЫМИ`.

**Константа** — `readonly`: менять нельзя.

```bash run
readonly TAX=5
echo "налог $TAX %"
TAX=7
echo "код: $?"
```

**Окружение.** Переменная живёт только в твоей оболочке. Чтобы её увидели **запущенные тобой программы** (дочерние процессы), её нужно *экспортировать*:

```bash run
SHOP="Bean"
bash -c 'echo "дочерний видит: [$SHOP]"'
export SHOP
bash -c 'echo "после export: [$SHOP]"'
echo "$HOME"
echo "$PWD"
env | grep '^SHOP='
```

`bash -c '…'` запускает новую оболочку с этой командой — то есть дочерний процесс. Одинарные кавычки нужны, чтобы `$SHOP` раскрыл уже дочерний bash, а не наш (про кавычки — следующий шаг). `env` печатает всё окружение; `HOME`, `PATH`, `PWD` существуют сразу, их задаёт система.

### result
```out auto
```

`TAX=7` не сработало: `readonly variable`, а код `1` (не ноль) означает ошибку. Без `export` дочерний процесс переменную не видит, с `export` — видит.

### why
Переменные — основа любого скрипта: пути, имена, настройки лежат в них. А различие «моя переменная / переменная окружения» нужно, чтобы понимать, почему один скрипт видит настройку другого, а другой нет (например, пароль, переданный деплой-скрипту через окружение).

### deep Как ещё можно
- `unset имя` — удалить переменную.
- Присвоить на один запуск: `SHOP=Bean bash -c 'echo $SHOP'` — переменная существует только для этой команды.
- `declare -p имя` — показать, как переменная устроена (тип, `readonly`, экспорт).
- `printenv` и `env` — почти одно и то же.

### deep Если не получилось
- **Переменная «пустая»** — проверь опечатку в имени (`$nmae`) и регистр (`$Name` ≠ `$name`): bash молча подставляет пустоту.
- **`bash: TAX: readonly variable`** — это правильная реакция: ты запретила изменение. В новом контейнере `readonly` пропадает.

## 2.3 Кавычки, подстановка команд и арифметика | short: Кавычки и подстановки | est: ~30 мин
### intro
**Слова шага:** *кавычки*, *раскрытие слов (word splitting)*, `$(команда)`, `$((выражение))`, *экранирование*.

Главное правило оболочки: **она делит строку на слова по пробелам**. Кавычки решают, сколько слов получится и что будет раскрыто.

```bash run
item="iced latte"
printf '[%s]\n' $item
printf '[%s]\n' "$item"
printf '[%s]\n' '$item'
```

**Команда по частям.** `printf '[%s]\n' …` печатает каждое слово в скобках на своей строке (`%s` — «вставь строку», `\n` — перевод строки), поэтому видно, сколько слов получила команда. Без кавычек `$item` разбилось на **два** слова (`iced`, `latte`); в двойных — осталось одно; в одинарных — `$item` не раскрылось вообще.

| Вид | Что внутри раскрывается | Пример |
|---|---|---|
| без кавычек | всё, и результат делится на слова | `echo $item` |
| `"…"` двойные | переменные `$x`, подстановки `$(…)` и `$((…))`; слова не делятся | `"цена: $price"` |
| `'…'` одинарные | **ничего**, всё буквально | `'$price'` |
| `\` | экранирует следующий символ | `\$price`, `\"` |

```bash run
echo "цена: \$price = $price"
echo 'цена: $price'
echo "он сказал \"привет\""
echo $'табуляция:\tи перенос\nстроки'
```

`$'…'` — особая форма, в которой работают `\t` и `\n`.

**Подстановка команды `$(…)`** подставляет в строку вывод команды:

```bash run
cd /work/coffeeops
echo "в папке orders файлов: $(ls orders | wc -l)"
files=$(ls orders)
echo "$files"
```

Старая запись с обратными кавычками `` `ls` `` делает то же самое, но не вкладывается и плохо читается — не используй её, но узнавай в чужих скриптах.

**Арифметика `$((…))`** считает **целые** числа:

```bash run
qty=3
price=180
echo $((qty * price))
echo $((7 / 2))
echo $((7 % 2))
echo $(( (qty + 1) * 2 ))
```

### result
```out auto
```

`7 / 2` дало `3`: дробной части нет, это *целочисленное* деление; `7 % 2` — остаток. Для дробей придётся взять `awk` (сессия 3).

### why
Ошибки с кавычками — причина большинства «странных» багов: файл с пробелом в имени, пустая переменная, исчезнувшая звёздочка. Если в кавычках **всегда** брать переменные (`"$x"`), половина проблем не возникнет. Эту привычку мы закрепим в следующем шаге.

### deep Как ещё можно
- Склейка кавычек: `'одинарные '"$item"' и двойные'`.
- Многострочные строки — внутри кавычек можно переносить строки; для больших кусков есть here-doc (сессия 6).
- Вложенность: `$(echo $(date +%Y))` работает; в обратных кавычках — нет.

### deep Если не получилось
- **`bash: 3 * 180: command not found`** — ты написала `$(qty * price)` с одной скобкой: это подстановка команды. Арифметика — две скобки: `$((…))`.
- **`bash: unexpected EOF while looking for matching '"'`** — не закрыта кавычка.

- Что выведет `echo '$HOME'` и `echo "$HOME"`?

## 2.4 Аргументы скрипта | short: Аргументы | est: ~30 мин
### intro
**Слова шага:** *аргумент*, *позиционные параметры* `$1 $2`, `$0`, `$#`, `$@`, `shift`, *значение по умолчанию*.

Всё, что ты пишешь после имени скрипта, — **аргументы**. Внутри скрипта они доступны как `$1`, `$2`, … (позиционные параметры). Создадим скрипт, который их показывает:

```bash run
cd /work/coffeeops
cat > bin/args.sh <<'EOF'
#!/usr/bin/env bash
echo "скрипт: $0"
echo "первый: $1, второй: $2"
echo "всего аргументов: $#"
printf '[%s] ' "$@"; echo
shift
echo "после shift первый: $1, всего: $#"
EOF
chmod +x bin/args.sh
./bin/args.sh latte 2 "hot and strong"
```

**Что здесь:** `$0` — имя скрипта; `$1`, `$2` — первый и второй аргументы (`"hot and strong"` в кавычках — один аргумент); `$#` — сколько всего; `"$@"` — все аргументы **по отдельности** (как отдельные слова); `shift` — «сдвинуть»: выбросить `$1`, а остальные сдвинуть влево.

Разница `"$@"` и `"$*"`:

```bash run
cat > bin/all.sh <<'EOF'
#!/usr/bin/env bash
printf 'через "$@": '; printf '[%s]' "$@"; echo
printf 'через "$*": '; printf '[%s]' "$*"; echo
EOF
chmod +x bin/all.sh
./bin/all.sh a "b c" d
```

`"$@"` сохраняет границы аргументов (получилось три слова), а `"$*"` склеивает всё в одну строку. В скриптах почти всегда нужен именно `"$@"`.

**Значения по умолчанию и обязательные аргументы:**

```bash run
cat > bin/defaults.sh <<'EOF'
#!/usr/bin/env bash
item="${1:-latte}"
qty="${2:-1}"
need="${3:?укажи третий аргумент}"
echo "item=$item qty=$qty need=$need"
EOF
chmod +x bin/defaults.sh
./bin/defaults.sh
echo "код: $?"
./bin/defaults.sh tea 2 yes
```

`${1:-latte}` — «значение `$1`, а если пусто — `latte`»; `${3:?текст}` — «если пусто, напечатай текст и **останови скрипт** с ошибкой».

### result
```out auto
```

### why
Скрипт без аргументов — одноразовый. С аргументами он превращается в инструмент: `order.sh latte 2`, `backup.sh /data`. А `${1:?…}` и `${1:-…}` — быстрый способ сделать скрипт безопасным и удобным, не усложняя код.

### deep Как ещё можно
- `$10` не работает так, как кажется: bash читает его как `$1` и цифру `0`. Для десятого аргумента: `${10}`.
- `$$` — номер процесса самого скрипта, `$!` — номер последнего фонового, `$_` — последний аргумент прошлой команды.
- `"$@"` и пустой список: если аргументов нет, `"$@"` не даёт ни одного слова, а `"$*"` — одно пустое.

### deep Если не получилось
- **`./bin/args.sh: line 6: shift: shift count out of range`** — нечего сдвигать (нет аргументов). Это ошибка только при `shift` в пустом списке.
- **Лишние/пропавшие слова** — забыты кавычки у `"$@"`.

## 2.5 🔨 Сломать → починить: пробелы и кавычки | short: Сломать → починить | est: ~25 мин
### intro
:::trap Сломать → починить
Четыре ошибки, с которых начинают почти все. Воспроизведи и почини каждую.
:::

**Ошибка 1 — пробелы вокруг `=`:**

```bash run
cd /work/coffeeops
x = 5
drink=Latte Grande
echo "drink=[$drink]"
```

В первом случае bash видит команду `x` с аргументами `=` и `5`; во втором — переменную `drink=Latte`, заданную на один запуск для команды `Grande`, поэтому в самой оболочке `drink` пуста. **Почини:** `x=5` и `drink="Latte Grande"`.

**Ошибка 2 — файл с пробелом, забытые кавычки.** Создадим файл с пробелом и попробуем удалить:

```bash run
touch "iced latte.txt"
ls
rm iced latte.txt
echo "код: $?"
```

Без кавычек `rm` получила **два** имени (`iced` и `latte.txt`); таких файлов нет — ошибки, а настоящий файл остался. **Почини:** `rm "iced latte.txt"`.

```bash run
rm "iced latte.txt"
ls
```

**Ошибка 3 — неверный shebang.** В контейнере bash лежит не в `/bin`:

```bash run
command -v bash
cat > bin/badshebang.sh <<'EOF'
#!/bin/bash
echo "hi"
EOF
chmod +x bin/badshebang.sh
./bin/badshebang.sh
```

**Почини:** замени первую строку на `#!/usr/bin/env bash` — она ищет bash в `PATH`.

**Ошибка 4 — пустая переменная и опасное `rm`.** Самая коварная:

```bash run
mkdir -p tmp-demo/keep
dir=""
echo rm -r "$dir"/keep
```

Мы **намеренно напечатали** команду через `echo`, а не выполнили. Если бы `dir` была пуста и мы написали `rm -r $dir/keep`, получилось бы `rm -r /keep` — удаление из корня. **Правило:** когда в команде есть переменная и удаление, сначала `echo`; в скриптах используй `"${dir:?}"` (остановит скрипт, если пусто).

Теперь та же защита `:?` в настоящем скрипте. Он остановится, не дойдя до `rm`:

```bash run
cat > bin/danger.sh <<'EOF'
#!/usr/bin/env bash
dir=""
rm -r "${dir:?папка не задана}"/keep
echo "эта строка не выполнится"
EOF
chmod +x bin/danger.sh
./bin/danger.sh
echo "код: $?"
rm -r tmp-demo bin/danger.sh
```

### result
```out auto
```

### why
Эти четыре ошибки дают больше половины проблем с первыми скриптами. Теперь ты узнаёшь их по сообщению. А привычка «переменная — всегда в кавычках и с `:?`, если удаляешь» защитит от потери данных.

### deep Как ещё можно
- Проверка скриптов на такие ошибки автоматически — `shellcheck` (сессия 5): он напишет «Double quote to prevent globbing and word splitting» там, где забыты кавычки.
- `set -u` (сессия 4) превращает обращение к необъявленной переменной в ошибку.

### deep Если не получилось
- **`rm: cannot remove 'x': No such file or directory`** — именно то, что мы и показываем; почини кавычками.
- **В `tmp-demo` остался мусор** — удали вручную: `rm -r tmp-demo` (проверь `ls` перед этим).

- Почему `drink=Latte Grande` не присваивает значение, и как правильно?
- Как удалить файл с пробелом в имени? Как создать такой?

## 2.6 Проект: order.sh | short: Скрипт order.sh | est: ~30 мин
### intro
**Слова шага:** *параметры скрипта*, *арифметика*, *вывод*, *код завершения*.

Соберём из всего сказанного первый настоящий скрипт CoffeeOps — `bin/order.sh`: принимает товар, количество и цену, считает сумму.

```bash run
cd /work/coffeeops
cat > bin/order.sh <<'EOF'
#!/usr/bin/env bash
# Использование: order.sh ТОВАР [КОЛИЧЕСТВО] [ЦЕНА]
item="${1:?укажи товар, например: order.sh latte 2}"
qty="${2:-1}"
price="${3:-150}"
total=$((qty * price))
echo "Заказ: $item x $qty = $total руб."
EOF
chmod +x bin/order.sh
./bin/order.sh latte 2
./bin/order.sh espresso 3 120
./bin/order.sh tea
./bin/order.sh
echo "код: $?"
```

**По частям.** `item="${1:?…}"` — первый аргумент обязателен, иначе скрипт останавливается с понятным сообщением; `qty="${2:-1}"` и `price="${3:-150}"` — необязательные с умолчаниями; `total=$((qty * price))` — арифметика; последняя строка — вывод.

### result
```out auto
```

Без аргументов скрипт сообщил, чего не хватает, и завершился с ненулевым кодом. В сессии 3 мы научимся делать ветвления и заменим эту ошибку «красивой» справкой с кодом 2.

### why
Это шаблон, по которому устроено большинство небольших утилит: разобрать аргументы → подставить умолчания → сделать работу → вывести результат. Все следующие скрипты проекта будут расти из него.

### deep Как ещё можно
- Вместо числа в `price` можно брать цену из таблицы; мы сделаем это через `case` (сессия 3) и массивы (сессия 7).
- Чтобы запускать скрипт без `./bin/`, добавь папку в `PATH`: `export PATH="$PATH:/work/coffeeops/bin"` — тогда `order.sh latte 2` работает из любой папки.

### deep Если не получилось
- **`arithmetic syntax error`** — в `qty` или `price` попало не число (например, `order.sh latte two`). Проверку ввода добавим в сессии 3.
- **`bad interpreter`** — неверный shebang; см. шаг 2.5.
