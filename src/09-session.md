## 9.1 Запуск по расписанию: cron | short: cron | est: ~30 мин
### intro
**Слова шага:** *планировщик*, `cron`, `crontab`, *расписание из пяти полей*, *демон*.

**cron** — служба, которая в нужное время запускает команды: ночной бэкап, проверка каждые пять минут, отчёт по понедельникам. Расписание хранится в таблице — **crontab**: одна строка — одно задание.

```text
┌───────── минута (0–59)
│ ┌─────── час (0–23)
│ │ ┌───── день месяца (1–31)
│ │ │ ┌─── месяц (1–12)
│ │ │ │ ┌─ день недели (0–7, 0 и 7 — воскресенье)
│ │ │ │ │
* * * * *  команда
```

Примеры расписаний:

| Запись | Когда |
|---|---|
| `* * * * *` | каждую минуту |
| `*/5 * * * *` | каждые 5 минут |
| `30 2 * * *` | каждый день в 02:30 |
| `0 9 * * 1-5` | по будням в 09:00 |
| `0 0 1 * *` | первого числа каждого месяца в полночь |

Поставим бэкап проекта на **каждую минуту** (для проверки; в жизни — реже). Вывод и ошибки задания сохраним в журнал — у cron нет экрана:

```bash run
cd /work/coffeeops
cat > tmp/crontab.txt <<'EOF'
# минута час день месяц день_недели команда
* * * * * /work/coffeeops/bin/backup.sh >> /work/coffeeops/logs/cron.log 2>&1
EOF
crontab tmp/crontab.txt
crontab -l
crond -b -L /work/coffeeops/logs/crond.log
sleep 65
echo "--- журнал задания:"
cat logs/cron.log
crontab -r
pkill crond || true
```

**По частям.** `crontab файл` — установить таблицу из файла (`crontab -l` показывает, `crontab -r` удаляет); `crond -b` — запустить службу в фоне (в обычной системе она уже работает); `>> журнал 2>&1` — дописывать вывод и ошибки в журнал (шаг 6.1); `sleep 65` — подождать, пока пройдёт минута.

Что стоит помнить про cron:

- **Окружение скупое.** У задания почти пустой `PATH` и нет твоих переменных: пиши полные пути (`/work/coffeeops/bin/backup.sh`) и не рассчитывай на привычное окружение.
- **Всегда перенаправляй вывод** в журнал; иначе ошибки уйдут «в никуда» (или в почту).
- **Задание не должно зависеть от терминала:** никаких `read` и цветов.
- В нашем контейнере cron работает, пока работает контейнер; на сервере — постоянно.

### result
```out auto
```

### why
Автоматический запуск — смысл большинства скриптов: бэкапы, проверки, отчёты. Правила «полные пути, вывод в журнал, без терминала» превращают скрипт из «работает у меня в консоли» в надёжное задание.

### deep Как ещё можно
- На **macOS** вместо cron принято использовать `launchd` (файлы `.plist` в `~/Library/LaunchAgents`); `cron` там тоже есть, но менее надёжен. На Linux-серверах всё чаще применяют таймеры `systemd`, но cron остаётся самым простым и повсеместным.
- Защита от наложения: если задание выполняется дольше минуты, запустится второе. Делают файл-замок (мы сделаем в `deploy.sh`) или команду `flock -n`.
- Проверить синтаксис расписания удобно на сайте `crontab.guru`.

### deep Если не получилось
- **Журнал пуст** — прошло меньше минуты или `crond` не запущен: проверь `pgrep crond`.
- **Задание «не находит» команду** — используется короткое имя вместо полного пути.
- **`crontab: command not found`** — образ собран без нужных пакетов; пересобери образ (шаг 1.2).

## 9.2 Деплой-скрипт: релизы и символическая ссылка | short: Деплой-скрипт | est: ~40 мин
### intro
**Слова шага:** *деплой (развёртывание)*, *релиз*, *символическая ссылка*, *атомарная замена*, *сухой запуск*, *замок*.

**Деплой** — доставка новой версии программы туда, где она работает. Простая и надёжная схема, которой пользуются тысячи проектов:

```text
deploy/
  releases/
    1.0-ab12cd34/    ← каждая версия лежит в своей папке
    1.1-ef56ab78/
  current → releases/1.1-ef56ab78   ← ссылка на «живую» версию
```

Сервис всегда запускается из `deploy/current`. Чтобы выкатить новую версию, мы кладём её в **новую** папку и **переключаем ссылку**. Переключение мгновенное (замена ссылки — одна атомарная операция), а предыдущая версия остаётся на диске: откат — это переключить ссылку обратно.

Подготовим «приложение»: папка `app/` с версией и проверкой здоровья (health check) — маленьким скриптом, который отвечает «сервис в порядке или нет».

```bash run
cd /work/coffeeops
mkdir -p app
echo "1.0" > app/VERSION
cat > app/healthcheck.sh <<'EOF'
#!/usr/bin/env bash
# Проверка здоровья: версия задана и не помечена как сломанная
cd "$(dirname "${BASH_SOURCE[0]}")" || exit 1
[[ -s VERSION ]] || { echo "нет файла VERSION" >&2; exit 1; }
[[ "$(cat VERSION)" != *broken* ]] || { echo "версия помечена как сломанная" >&2; exit 1; }
echo "здоров: версия $(cat VERSION)"
EOF
chmod +x app/healthcheck.sh
app/healthcheck.sh
```

Теперь сам деплой-скрипт. Читай его по блокам (разбор — ниже):

```bash run
cat > bin/deploy.sh <<'EOF'
#!/usr/bin/env bash
# Развёртывание CoffeeOps: релизы + символическая ссылка current.
# Использование: deploy.sh [-n] [-k КОЛИЧЕСТВО]
#   -n  сухой запуск: показать действия, ничего не менять
#   -k  сколько релизов хранить (по умолчанию 3)
set -euo pipefail
ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
# shellcheck source=../lib/common.sh
source "$ROOT/lib/common.sh"

usage() { echo "Использование: deploy.sh [-n] [-k КОЛИЧЕСТВО]"; }

dry=0
keep=3
while getopts ":nk:h" opt; do
  case "$opt" in
    n) dry=1 ;;
    k) keep="$OPTARG" ;;
    h) usage; exit 0 ;;
    *) usage >&2; exit 2 ;;
  esac
done

app="$ROOT/app"
releases="$ROOT/deploy/releases"
current="$ROOT/deploy/current"
lock="$ROOT/deploy/.lock"

# выполнить команду или (при -n) только показать её
run() {
  if (( dry )); then log "[сухой запуск] $*"; else "$@"; fi
}

# смена ссылки одной атомарной операцией
switch_to() {
  run ln -sfn "$1" "$current.new"
  run mv -T "$current.new" "$current"
}

preflight() {
  local tool
  for tool in cp ln mv sha256sum find; do
    command -v "$tool" > /dev/null || die "нет команды '$tool'" 3
  done
  [[ -d "$app" ]] || die "нет папки приложения '$app'" 2
  [[ -s "$app/VERSION" ]] || die "в '$app' нет файла VERSION" 2
  if ! [[ "$keep" =~ ^[0-9]+$ ]] || (( keep < 2 )); then
    die "-k: нужно число не меньше 2, а не '$keep'" 2
  fi
}

# хеш содержимого приложения: тот же код — то же имя релиза
app_hash() {
  (cd "$app" && find . -type f -print0 | sort -z | xargs -0 sha256sum | sha256sum | cut -c1-8)
}

preflight
name="$(cat "$app/VERSION")-$(app_hash)"
target="$releases/$name"
previous=""
[[ -L "$current" ]] && previous="$(readlink "$current")"

# идемпотентность: этот релиз уже развёрнут — делать нечего
if [[ "$previous" == "$target" ]]; then
  log "релиз $name уже развёрнут, ничего не делаю"
  exit 0
fi

# замок: не даём запустить два деплоя одновременно
if (( ! dry )); then
  mkdir -p "$ROOT/deploy"
  mkdir "$lock" 2> /dev/null || die "деплой уже идёт (есть $lock)" 4
  trap 'rmdir "$lock"' EXIT
fi

log "развёртываю $name (сейчас: ${previous##*/})"
run mkdir -p "$releases"
run cp -a "$app" "$target"
switch_to "$target"

if (( dry )); then
  log "[сухой запуск] проверка: $current/healthcheck.sh"
  exit 0
fi

# проверка здоровья и откат при неудаче
if "$current/healthcheck.sh"; then
  log "проверка пройдена, релиз $name в работе"
else
  warn "проверка не прошла, откатываюсь"
  if [[ -n "$previous" ]]; then
    switch_to "$previous"
    log "возвращён предыдущий релиз ${previous##*/}"
  else
    rm -f "$current"
  fi
  rm -rf "$target"
  exit 1
fi

# уборка: оставляем только последние -k релизов
find "$releases" -mindepth 1 -maxdepth 1 -type d -printf '%T@ %p\n' \
  | sort -rn | tail -n +$((keep + 1)) | cut -d' ' -f2- | xargs -r rm -rf
EOF
chmod +x bin/deploy.sh
shellcheck bin/deploy.sh app/healthcheck.sh && echo "shellcheck: чисто"
```

**Разбор по частям.**

- **Сухой запуск `-n`.** Все изменяющие команды идут через функцию `run`: при `-n` она только печатает команду, иначе выполняет. Ты видишь план, не рискуя ничем.
- **`switch_to`.** Сначала создаётся новая ссылка рядом (`ln -sfn`), затем она переименовывается поверх старой (`mv -T`). Переименование — атомарная операция: в любой момент `current` указывает либо на старую версию, либо на новую, но никогда «в никуда».
- **`preflight`.** Проверки окружения до всякой работы: есть ли нужные утилиты, папка приложения, файл версии, корректный параметр `-k`. Коды ошибок разные: 2 — неверное использование, 3 — нет команды.
- **`app_hash`.** Имя релиза = версия + 8 символов хеша содержимого. Не изменил код — получил то же имя, значит повторный запуск ничего не меняет.
- **Замок.** `mkdir` — атомарная операция: создать папку может только один процесс. Второй получит ошибку и остановится. `trap … EXIT` убирает замок при любом завершении.
- **Откат.** Если health check не прошёл — возвращаем ссылку на прежний релиз, удаляем неудачный и выходим с ошибкой.
- **Уборка.** Оставляем последние `-k` релизов, остальные удаляем.

### result
```out auto
```

### why
Эта схема — простой «рабочий» деплой, который переносится почти на любой сервер. Сухой запуск, замок, health check и откат — те же приёмы, что в больших системах: просто здесь они помещаются на один экран. В Docker-лабе похожая последовательность будет разворачивать контейнер.

### deep Как ещё можно
- Вместо `cp -a` релиз может скачиваться (`git clone`, `curl … | tar`), собираться (`docker build`) или распаковываться из архива — схема «папка + ссылка» остаётся.
- Для сервиса, запущенного в Docker, шаг «переключить ссылку» заменяется на `docker run` новой версии и проверку её здоровья; предыдущий контейнер остаётся для отката.
- `ln -sfn` — по буквам: `s` символическая ссылка, `f` заменить существующую, `n` не заходить в папку, на которую указывает ссылка.

### deep Если не получилось
- **`mv: unrecognized option: T`** — на macOS (BSD `mv`) такого ключа нет; в нашем контейнере (GNU coreutils) он работает.
- **`деплой уже идёт`, хотя ничего не запущено** — остался замок после аварии: удали `deploy/.lock` вручную (`rmdir deploy/.lock`).

## 9.3 Запуск, повтор, откат | short: Запуск и откат | est: ~30 мин
### intro
**Слова шага:** *идемпотентность*, *откат (rollback)*, *health check*.

**Идемпотентность** — свойство операции: сколько раз ни выполни, результат тот же. Для деплоя это значит: повторный запуск ничего не ломает. Проверим всё на деле.

```bash run
cd /work/coffeeops
echo "=== 1. сухой запуск"
./bin/deploy.sh -n
ls deploy 2>&1 | head -n 3
echo "=== 2. первый деплой"
./bin/deploy.sh
echo "=== 3. повторный деплой (тот же код)"
./bin/deploy.sh
echo "=== 4. новая версия"
echo "1.1" > app/VERSION
./bin/deploy.sh
readlink deploy/current
ls deploy/releases
```

**Откат при сбое.** Выкатим версию, помеченную «сломанной» — health check это заметит:

```bash run
echo "=== 5. сломанная версия"
echo "1.2-broken" > app/VERSION
./bin/deploy.sh
echo "код: $?"
echo "current указывает на: $(readlink deploy/current)"
ls deploy/releases
echo "=== 6. возвращаем рабочую версию"
echo "1.1" > app/VERSION
./bin/deploy.sh
```

**Замок:**

```bash run
echo "=== 7. замок"
mkdir deploy/.lock
echo "1.3" > app/VERSION
./bin/deploy.sh
echo "код: $?"
rmdir deploy/.lock
./bin/deploy.sh
echo "1.1" > app/VERSION
```

### result
```out auto
```

### why
Именно такие проверки отличают скрипт «для себя» от скрипта, которому можно доверить сервер: повторный запуск безопасен, сломанная версия не заменяет рабочую, два деплоя не мешают друг другу. Ты увидела это своими глазами, а не поверила на слово.

### deep Как ещё можно
- Реальный health check — это запрос к сервису (`curl -fsS http://localhost:8080/health`), проверка порта, вызов тестовой команды; принцип тот же: код возврата 0 — «в порядке».
- Откатить вручную на любой из хранящихся релизов: `ln -sfn deploy/releases/<имя> deploy/current.new && mv -T deploy/current.new deploy/current`.
- Уведомления об ошибках: в `else` ветке можно отправить сообщение (`curl` в чат, письмо) — об этом можно подумать, когда скрипт запускается по расписанию.

### deep Если не получилось
- **В пункте 5 нет отката** — в `deploy.sh` пропущена ветка `else` у health check; сверь с листингом шага 9.2.
- **Релизы копятся** — уборка оставляет `-k` штук (по умолчанию 3); после нескольких версий лишние пропадут.

## 9.4 🔨 Production Hell: сломанный deploy.sh | short: Production Hell | est: ~35 мин
### intro
:::trap Production Hell
Тебе достался чужой деплой-скрипт. Он «работает на машине автора», но на сервере ломается. В нём **пять** ошибок, и все из тех, что мы разбирали. Найди и исправь — и только потом смотри ответы.
:::

Создадим скрипт и песочницу для него. Всё остаётся в папке `playground/hell`, основной проект не затрагивается:

```bash run
cd /work/coffeeops
mkdir -p playground/hell/app playground/hell/deploy
echo "2.0" > playground/hell/app/VERSION
printf '#!/usr/bin/env bash\nexit 0\n' > playground/hell/app/healthcheck.sh
chmod +x playground/hell/app/healthcheck.sh
cat > playground/hell/deploy-broken.sh <<'EOF'
#!/bin/bash
APP=$PWD/app
REL=$PWD/deploy/releases
mkdir $REL
name=release-$(date +%s)
cp -r $APP $REL/$name
ln -s $REL/$name deploy/current
./deploy/current/healthcheck.sh
echo "Деплой завершён успешно!"
EOF
chmod +x playground/hell/deploy-broken.sh
cd playground/hell
./deploy-broken.sh
echo "код: $?"
```

Первая ошибка видна сразу. Обойдём её, запустив через `bash`, и посмотрим, что ещё. Первый запуск проходит, а на втором и третьем скрипт жалуется на ошибки — но всё равно рапортует об «успехе». На третьем запуске мы подменим `healthcheck.sh` на проверку, которая всегда падает (и уберём старую ссылку, чтобы проверка дошла до нового релиза):

```bash run
bash deploy-broken.sh
echo "код: $?"
echo "--- второй запуск:"
sleep 1
bash deploy-broken.sh
echo "код: $?"
echo "--- третий запуск, health check теперь падает:"
printf '#!/usr/bin/env bash\nexit 1\n' > app/healthcheck.sh
rm deploy/current
sleep 1
bash deploy-broken.sh
echo "код: $?"
```

Подсказки: запусти `shellcheck deploy-broken.sh` и прочитай каждое замечание; подумай, что случится при повторном запуске и когда `healthcheck.sh` вернёт ошибку; вспомни шаги 2.5, 4.3, 4.5 и 9.2. Исправь скрипт в файле `deploy-fixed.sh` (на основе ответов ниже или нашего `deploy.sh`).

```bash run
shellcheck deploy-broken.sh
```

### result
```out auto
```

**Ответы — пять ошибок:**

1. **`#!/bin/bash`** — bash лежит не везде в `/bin`. Правильно: `#!/usr/bin/env bash`.
2. **Нет `set -euo pipefail`** — скрипт идёт дальше после ошибок и в конце бодро пишет «успешно», даже если проверка упала.
3. **`mkdir $REL`** — нет `-p` (на втором запуске: «File exists»), нет кавычек (сломается на пути с пробелом); без кавычек и `cp -r $APP $REL/$name`.
4. **`ln -s` без `-f`/`-n`** — `ln -s` не заменяет уже существующую ссылку, поэтому новый релиз не включается; а если `current` указывает на папку, ссылка молча создаётся **внутри** этой папки. Правильно: `ln -sfn` и атомарная замена через `mv -T` (шаг 9.2).
5. **Результат `healthcheck.sh` не проверяется** — после запуска проверки нет `if`, а строка «успешно» печатается всегда (даже на третьем запуске, где проверка вернула ошибку); нет отката.

Исправленная версия — это по сути наш `bin/deploy.sh`, где каждая из этих ошибок закрыта.

### why
Реальные «ужасы продакшена» — не экзотика, а набор привычек: нет строгого режима, нет кавычек, нет проверки результата, ссылки без `-f`. Теперь ты узнаёшь их с первого взгляда — в чужом скрипте и в своём.

### deep Как ещё можно
- Проверяй скрипты на повторный запуск как отдельный пункт: «запустить два раза подряд» ловит половину проблем.
- Помимо `shellcheck` полезны `bash -n скрипт` (проверка синтаксиса без запуска) и `bash -x скрипт` (трассировка команд).

### deep Если не получилось
- **Скрипт сразу «исправился» сам** — ты запускаешь не из папки `playground/hell`: `deploy/` создаётся рядом с запущенным скриптом, проверь `pwd`.
- **Хочешь начать заново** — `rm -r playground/hell/deploy` (проверь путь `ls` перед удалением).

## 9.5 Итоговый проект: coffeeops.sh с подкомандами и тестами | short: coffeeops.sh и тесты | est: ~40 мин
### intro
**Слова шага:** *точка входа*, *подкоманды*, *тест*, *тестовый прогон*.

Соберём CoffeeOps в единый инструмент: `coffeeops.sh КОМАНДА …` (как `git commit`, `docker run`) и добавим тесты, которые проверяют, что скрипты по-прежнему работают.

```bash run
cd /work/coffeeops
cat > bin/coffeeops.sh <<'EOF'
#!/usr/bin/env bash
# CoffeeOps — единая точка входа. Использование: coffeeops.sh КОМАНДА [аргументы]
set -euo pipefail
ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
# shellcheck source=../lib/common.sh
source "$ROOT/lib/common.sh"

usage() {
  cat <<'TEXT'
Использование: coffeeops.sh КОМАНДА [аргументы]

Команды:
  order ТОВАР [N]   посчитать заказ
  stats             итоги по дням
  top [-n N]        топ товаров по числу заказов
  count             порции и выручка по товарам
  report [-m awk|bash]   отчёты по журналу
  backup            архив заказов
  deploy [-n]       развернуть сервис (-n — сухой запуск)
  test              запустить тесты
  help              эта справка
TEXT
}

cmd="${1:-help}"
if (( $# > 0 )); then shift; fi

case "$cmd" in
  order | stats | top | count | backup | deploy) exec "$ROOT/bin/$cmd.sh" "$@" ;;
  report)          exec "$ROOT/bin/logreport.sh" "$@" ;;
  test)            exec "$ROOT/tests/run.sh" "$@" ;;
  help | -h | --help) usage ;;
  *) usage >&2; die "неизвестная команда: $cmd" 2 ;;
esac
EOF
chmod +x bin/coffeeops.sh
./bin/coffeeops.sh help
./bin/coffeeops.sh order latte 2
./bin/coffeeops.sh fly
echo "код: $?"
```

**Тесты.** Тест — это маленький скрипт, который запускает наши программы и сравнивает результат с ожидаемым:

```bash run
mkdir -p tests
cat > tests/run.sh <<'EOF'
#!/usr/bin/env bash
# Тесты CoffeeOps. Использование: tests/run.sh
set -uo pipefail
ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
pass=0
fail=0

# check ИМЯ ОЖИДАЕМОЕ ФАКТИЧЕСКОЕ
check() {
  if [[ "$2" == "$3" ]]; then
    echo "ok    $1"; pass=$((pass + 1))
  else
    echo "FAIL  $1: ожидалось [$2], получено [$3]"; fail=$((fail + 1))
  fi
}

check "order: латте x2" "Заказ: latte x 2 = 360 руб." "$("$ROOT/bin/order.sh" latte 2 2>&1)"
"$ROOT/bin/order.sh" pizza > /dev/null 2>&1; check "order: неизвестный товар даёт код 2" 2 $?
"$ROOT/bin/order.sh" latte abc > /dev/null 2>&1; check "order: плохое число даёт код 2" 2 $?
check "stats: итого" "ИТОГО: 10400 руб." "$("$ROOT/bin/stats.sh" | grep ИТОГО)"
check "top: лидер" "tea" "$("$ROOT/bin/top.sh" -n 1 | awk '{ print $2 }')"
check "count: лидер по выручке" "cappuccino" "$("$ROOT/bin/count.sh" | sed -n 2p | awk '{ print $1 }')"
check "logreport: awk и bash совпадают" "$("$ROOT/bin/logreport.sh" -m awk)" "$("$ROOT/bin/logreport.sh" -m bash)"
"$ROOT/bin/deploy.sh" -n > /dev/null 2>&1; check "deploy: сухой запуск успешен" 0 $?

echo "пройдено: $pass, провалено: $fail"
(( fail == 0 ))
EOF
chmod +x tests/run.sh
./bin/coffeeops.sh test
echo "код тестов: $?"
```

### why
Единая точка входа превращает набор скриптов в **инструмент**: у него есть справка, подкоманды и тесты. Тесты нужны, чтобы смело менять код: сломал — тесты скажут сразу. Именно так выглядят настоящие небольшие утилиты командной строки.

### deep Как ещё можно
- Автодополнение подкоманд по [[Tab]] настраивается скриптом для bash (`complete -W "order stats top …" coffeeops.sh`).
- Для больших проектов тесты делают на готовых фреймворках (`bats`), но принцип тот же: запустить, сравнить, посчитать.
- Установить проект как команду: `ln -s /work/coffeeops/bin/coffeeops.sh /usr/local/bin/coffeeops` — и он вызывается из любой папки.
- Скрипты можно подключить в `cron` (шаг 9.1) и в GitHub Actions: `./bin/coffeeops.sh test` и `shellcheck` на каждый коммит.

### deep Если не получилось
- **Тест `stats: итого` падает** — данные другие: заново выполни `bash seed.sh`, он создаёт те же файлы (если ты правила `orders/*.csv`, ожидаемые числа изменятся).
- **`tests/run.sh: No such file`** — не создана папка `tests` или скрипт не сделан исполняемым.
